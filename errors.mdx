Documented error responses use a JSON object with `error` (a short error type) and `message` (a human-readable explanation). The exact message may vary by cause.

## Documented status codes

| Code | Meaning | What to check |
| --- | --- | --- |
| `400 Bad Request` | Missing or invalid request body; for updates, an invalid status or missing fields. | Check the JSON, required fields, and allowed values. For status, use `pending`, `in_progress`, or `done`. |
| `401 Unauthorized` | Missing or invalid API key. | Send `Authorization: Bearer <your_api_key>`. See [Authentication](/authentication). |
| `404 Not Found` | Project or task not found. | Check that the ID came from a creation response and is used in the correct route. Create the project before creating tasks. |

The codes above are defined in the specification for the corresponding operations. Success responses are `201` when creating a project or task and `200` when listing, updating, or deleting.

## Workflow dependencies

- Create a project before creating tasks. Project creation returns the `project_id`.
- Use the `project_id` to create tasks and list the project's tasks.
- Use the `task_id` returned when creating a task to update or delete it.
- Deletion is permanent.

## Initial response time

The server may take up to 60 seconds to respond to the first request. Wait for the response before retrying a creation request, as a retry may create another resource.

## Known specification limitations

- The specification lists only five operations: create a project; create, list, update, and delete tasks. See the **API Reference** group in the navigation.
- No operations are documented for listing projects, retrieving a single task, restoring a deleted task, or managing API keys.
- The contract does not document pagination, filters, rate limits, or retry policies. Do not assume these features are available.
